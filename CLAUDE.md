# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## State of the project

TicketNest is a demo booking platform for movies, buses and trains, designed as microservices. Right now the repo is **design docs plus an empty scaffold**: every app and the services other than `auth-service`, `api-gateway` and `catalog-service` contain only a placeholder `src/index.ts`. The real code is `packages/contracts`, `packages/config`, `packages/logger`, `packages/errors`, `packages/auth-middleware`, `packages/rate-limit`, `packages/service-runtime`, `packages/messaging` (the outbox writer and envelope builder, plus in its `/relay` entry the outbox relay loop and `AmqpEventPublisher`; auth-service is the first service to run the relay), the `services/api-gateway` (routing, token verification, rate limiting; see its bullet below) and the `services/auth-service` (health endpoints, the Prisma schema with its migrations, the user, role, refresh-token and outbox repositories, the routes `POST /v1/auth/register`, `login`, `refresh` and `logout`, `GET /v1/users/me` and the JWKS endpoint, and the outbox relay that publishes `user.registered` to RabbitMQ). `services/catalog-service` is the skeleton only (health endpoints on port 4002, a Dockerfile, Postgres readiness; no routes, Prisma schema or repositories yet). Do not assume a service, Dockerfile, database or broker exists; check first.

The source of truth for what to build is in `docs/`:

- `docs/prd.md`: requirements. Items marked **[Assumption]** (and listed in section 14) were never confirmed by the owner.
- `docs/architecture.md`: service boundaries, data ownership, the booking saga, outbox/inbox, idempotency, C4 diagrams, and the proposed ADR list (section 14). Decisions marked **[Rec]** are recommended defaults, not ratified.
- `docs/api/`: OpenAPI 3.1 for `auth-service` and `catalog-service`; `common.yaml` holds the shared error/pagination/header components both specs `$ref`.

## Commands

Requires **Node 24** (`.nvmrc`) and pnpm 12 (pinned by `packageManager`; `corepack enable`). `devEngines.runtime` makes pnpm refuse to run on any other Node (`ERR_PNPM_BAD_RUNTIME_VERSION`), and `npm`/`npx` run inside the repo are blocked too. Do not bypass it with `--runtime-on-fail`; switch Node (`fnm use`) instead.

```sh
pnpm install
pnpm lint                 # turbo: eslint in every workspace, then the test-layout check
pnpm typecheck            # turbo: tsc --noEmit in every workspace
pnpm test                 # turbo: vitest in every workspace (the integration tests of auth-service, rate-limit and messaging need Docker; auth-service's start Postgres, Redis and RabbitMQ, the broker through `@ticketnest/messaging/testing/rabbitmq`)
pnpm format:check         # prettier --check . (pnpm format to write)
pnpm build                # currently a no-op: no workspace defines a build script
```

Single workspace / single test:

```sh
pnpm --filter @ticketnest/contracts test
pnpm --filter @ticketnest/contracts exec vitest run test/contracts.test.ts -t "Money"
```

Local infrastructure (Docker Compose in `infra/docker/`: Postgres 17, Redis 8, RabbitMQ 4 with the management UI):

```sh
cp infra/docker/.env.example infra/docker/.env   # once; .env is git-ignored
pnpm infra:up      # start and wait until all three are healthy
pnpm infra:down    # stop; data volumes are kept
pnpm infra:reset   # DELETES all local data (volumes), then starts fresh
```

- Postgres has one database and one login role per service (`auth`/`auth_service`, `catalog`, `booking`, `payment`, `notification`). The init script runs only on an empty volume, so changing it or a DB password needs `pnpm infra:reset`.
- Host ports bind to `127.0.0.1` and come from `.env` (`*_HOST_PORT`); change one if it clashes with a local install. RabbitMQ UI: `http://localhost:15672`.
- The stack defines no exchanges or queues; the RabbitMQ topology belongs to service code (ADR-0005).

Docs checks (no script exists; run from a shell on Node 24):

```sh
npx @redocly/cli@1.34.5 lint docs/api/auth-service.openapi.yaml   # also catalog-service
```

Mermaid blocks in `docs/architecture.md` are validated by rendering them with `@mermaid-js/mermaid-cli` (`mmdc`); a literal `;` inside a sequence-diagram message breaks the parser.

## Git hooks and commit messages

Husky is installed by `pnpm install` (the root `prepare` script sets `core.hooksPath` to `.husky/_`).

- `pre-commit` runs lint-staged (`lint-staged.config.mjs`): `eslint --fix` from each file's own workspace (type-aware ESLint needs that cwd), then `prettier --write`. It fixes files and re-stages them; unfixable ESLint errors abort the commit.
- `commit-msg` runs commitlint (`commitlint.config.mjs`, `@commitlint/config-conventional`). Use Conventional Commits: `type(scope): lower-case subject`, no trailing period. Types: build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test.
- Never bypass with `--no-verify`. In CI, set `HUSKY=0` so `prepare` does not install hooks.

## Monorepo conventions that are not obvious

- **Workspaces:** `apps/*`, `services/*`, `packages/*`, all named `@ticketnest/<folder>`. Shared dependency versions live in the `catalog:` block of `pnpm-workspace.yaml`; reference them as `"catalog:"`, do not hard-code versions in workspace `package.json` files.
- **TypeScript is pinned to `~6.0.3`** because `typescript-eslint` does not support TypeScript 7 yet. Do not bump it until that changes.
- **Shared packages are just-in-time:** `@ticketnest/contracts` exports TypeScript source (`./src/*.ts`), with no build step. Consumers must transpile it (Next `transpilePackages`; services bundle them with esbuild). TS resolution is `Bundler`, `noEmit` everywhere, so there are no `.js` import extensions.
- **Env config:** every service validates its environment with `loadConfig(schema)` from `@ticketnest/config` as the first line of `src/main.ts`. The schema is `baseConfigSchema.extend({...})` (base: `NODE_ENV`, `PORT`, `LOG_LEVEL`). It throws `ConfigError` listing every bad variable, never their values; empty strings count as unset. Schemas several services need (`originListSchema`, `httpOriginSchema`, `trustProxyHopsSchema`, `shutdownTimeoutMsSchema`, `refreshReuseGraceMsSchema`) are exported from the package: use them, do not copy them. A service that runs the outbox relay spreads `outboxRelayConfigShape` (`RABBITMQ_URL`, `OUTBOX_RELAY_ENABLED`, `OUTBOX_RELAY_POLL_INTERVAL_MS`, `OUTBOX_RELAY_BATCH_SIZE`) into its `extend({...})` and calls `requireBrokerUrlWhenRelayEnabled` from its `superRefine`.
- **Logging:** services log through `createLogger({ serviceName, level, nodeEnvironment })` from `@ticketnest/logger`, built from the validated config (pino JSON, pretty only when `NODE_ENV=development`). Wrap each request or broker message in `runWithCorrelationId(id, work)` (id from the `X-Request-Id` header or the event's `correlationId`) and every line gets `correlationId`. Passwords, tokens, OTPs, secrets and `authorization`/`cookie` headers are redacted at the top level and one level down only, so never log objects nested deeper that may hold them.
- **Errors:** throw subclasses of `AppError` from `@ticketnest/errors` (`NotFoundError`, `ValidationError`, `UnauthorizedError`, `ForbiddenError`, `ConflictError`, `BadRequestError`); domain errors subclass these with a `code` (`SeatUnavailableError extends ConflictError`). Convert a failed Zod parse with `fromZodError(error, 'body' | 'query' | 'path')`. In Express 5 mount `handleUnmatchedRoute` then `createErrorHandler({ logger, getCorrelationId, isDebugInfoExposed })` from `@ticketnest/errors/express` last. It answers RFC 9457 `application/problem+json`; anything that is not an `AppError` becomes a generic 500, and 500s never carry `detail`, message or stack unless `isDebugInfoExposed` (development only). The core entry point has no Express dependency, and `ConfigError` is an `AppError`.
- **Strictness is high and enforced:** `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, and type-aware `strictTypeChecked` ESLint (floating promises are errors). Use `import { type X }` for type-only imports.
- **tsconfig presets** (`@ticketnest/tsconfig`): `node.json` for services, `library.json` for packages, `nextjs.json` for apps. `types` defaults to `[]`, so Node types come only from `node.json`. The ESLint `next` preset and Next TS plugin are deliberately deferred until a Next app is bootstrapped.
- **Prettier ignores `docs/`** on purpose (hand-formatted tables, Mermaid, flow-style YAML). Don't run it over docs.
- **Service skeleton (`services/auth-service` is the template; copy it for the next service):** the parts every service shares live in `packages/service-runtime` (`createShutdown`, `DependencyCheck`, and from `/express` `createHealthRouter`, `handleRequestId` and `createRequestLogger`): fix them there, never in a service. `src/app.ts` exports `createApp(dependencies)` (middleware, health router, error handler; no sockets, no clients) and `src/server.ts` is the composition root that builds the pg `Pool`, the Redis client and the server. Tests import `createApp` with fakes (Supertest, `test/support/create-test-app.ts`). Feature routers are passed in through `routers`. `/health/live` never touches a dependency; `/health/ready` checks Postgres and Redis (2s timeout each), reports only `up`/`down` and never driver messages, and returns 503 once shutdown starts. SIGTERM/SIGINT stop the listener, let in-flight requests finish, close the pool and Redis (`closeRedisClient` from `packages/rate-limit` drops the socket when `QUIT` cannot be sent), then exit (forced after `SHUTDOWN_TIMEOUT_MS`). A service gets `dev`/`build` scripts only when it becomes real: `dev` is `tsx watch --env-file=.env`, `build` is esbuild into one `dist/server.cjs`.
- **Passwords:** hashed with argon2id through Node's built-in `crypto.argon2` (Node 24.7+), behind the `PasswordHasher` interface in `services/auth-service/src/auth/`. Parameters are named constants at the OWASP minimum and are read back from the stored PHC string on verify. See ADR-0013 and `.claude/rules/security.md`. `POST /v1/auth/register` may answer 409 for a taken email, so it is rate limited by IP and by email (see the Rate limiting bullet).
- **Events (auth-service):** `RegisterService` writes a `user.registered` outbox row in the same `unitOfWork.run` as `userRepository.create`, through `UserRegisteredEventRecorder` (`src/auth/`) and `OutboxWriter` from `packages/messaging`; `PrismaOutboxRepository` (`src/repositories/`) is the only code that inserts into the `outbox` table (`PrismaOutboxRelayRepository` is the only code that updates its rows) and refuses a transaction handle that did not come from `PrismaUnitOfWork`. The payload is `userId`, `roleKey` and `registeredAt` only (no email, name, phone or hash); the correlation id is the request's `X-Request-Id` (already limited to 128 safe characters by `handleRequestId`). The relay publishes the rows: `composeOutboxRelay` (`src/compose-outbox-relay.ts`, part of the composition root) builds `PrismaOutboxRelayRepository`, `AmqpEventPublisher` (domain `auth`, exchange `auth.events`) and `OutboxRelay` from `packages/messaging/relay`, and `server.ts` creates the Prisma client once and starts the relay after `app.listen`. `createShutdownResources` (`src/`) fixes the shutdown order (`outbox-relay`, `amqp`, Postgres, Redis) and `createReadinessChecks` (`src/health/`) keeps the broker out of `/health/ready`; both are unit tested, so change them there, not in `server.ts`. Config: `RABBITMQ_URL` (required unless `OUTBOX_RELAY_ENABLED=false`, which builds nothing and leaves the rows unpublished), `OUTBOX_RELAY_POLL_INTERVAL_MS`, `OUTBOX_RELAY_BATCH_SIZE`. The relay never affects `/health/ready`: a broker outage only delays publishing. Keep `SHUTDOWN_TIMEOUT_MS` above the relay's 5 s stop wait plus the AMQP closes (up to 4 s); nothing enforces it. A row that fails ten times, or holds an invalid envelope, gets `failed_at` and waits for a person: follow `docs/runbooks/outbox-failed-rows.md`, and never put a payload in a ticket. A new event needs its schema in `packages/contracts`, a recorder like this one, and a test that its stored payload has exactly the expected keys. See ADR-0005, ADR-0007 and ADR-0011.
- **Login and tokens (auth-service):** `LoginService` (`src/auth/login.service.ts`) answers every failure with one `InvalidCredentialsError` (401) and runs exactly one argon2id verify per attempt (a startup-made dummy hash when there is no usable stored hash). Access tokens are EdDSA JWTs signed by `EdDsaTokenService` behind the `TokenService` interface; refresh tokens are 256 random bits stored as SHA-256. The service needs `JWT_PRIVATE_KEY` (base64 PKCS#8 PEM, Ed25519), `JWT_ISSUER` and `JWT_AUDIENCE` and refuses to start without them; the `kid` is the key's RFC 7638 thumbprint, not configured (`.env.example` explains how to generate a local key; tests generate keys at runtime). `permissions[]` is issued empty until the permission catalogue is seeded.
- **Refresh (auth-service):** `RefreshService` (`src/auth/refresh.service.ts`) rotates in one transaction (insert the successor, then a conditional `markRotated`; losing a race throws `RotationLostError`, which rolls the insert back). Every failure is the same `InvalidRefreshTokenError` (401); the reason goes to the log. A replay of a rotated token within `REFRESH_REUSE_GRACE_MS` (env, default 10 s, 0 to 30 000, 0 = strict; schema in `packages/config`) is a plain 401 that leaves the family alone; later it revokes the whole family in its own committed transaction. `POST /v1/auth/refresh` has the same rate-limit and gateway-exposure rule as login.
- **Logout (auth-service):** `LogoutService` (`src/auth/logout.service.ts`) hashes the presented refresh token and, when found, calls `revokeFamily` for its whole family. It needs no access token (spec `security: []`), always answers 204 for a well-formed body (422 only for a bad body shape) and logs the outcome with ids only. Access JWTs already issued stay valid until they expire (ADR-0013 weak point 1; no denylist). "Log out of all devices" is not built. It is rate limited by IP like the others (see the Rate limiting bullet).
- **Access-token verification (`packages/auth-middleware`):** the core entry exports `JwtAccessTokenVerifier` (behind the `AccessTokenVerifier` interface), the `KeyResolver` implementations `StaticKeyResolver` (a `kid` -> key map in memory) and `JwksKeyResolver` (cache, `ETag`, one refetch per cooldown on an unknown `kid`, bounded stale-if-error, over a `JwksFetcher` with `HttpJwksFetcher` as the HTTP one), `InvalidAccessTokenError` and `KeySetUnavailableError` (503, never 401). `/express` exports `createAuthenticateMiddleware`, `createOptionalAuthenticateMiddleware` (no `Authorization` header = anonymous; a header that is sent must be valid or the answer is 401), `getAuthenticatedPrincipal`, `findAuthenticatedPrincipal` (`undefined` for anonymous) and `setAuthenticatedPrincipal`. Controllers read the caller only through `getAuthenticatedPrincipal`. A service builds the verifier in its composition root: auth-service with `createLocalAccessTokenVerifier` (`src/auth/`: `StaticKeyResolver` over its own key set and clock tolerance 0, because signer and verifier share one clock), every other service and the gateway with `JwksKeyResolver` over `HttpJwksFetcher`. Permission/role guards and the `x-recent-login` check are not built yet. See ADR-0013.
- **Current user (auth-service):** `GET /v1/users/me` (`src/users/`) sits behind the shared `authenticate` middleware. Every failure is one `InvalidAccessTokenError` (401); the user and role are re-read from the database and a missing or non-`ACTIVE` user is the same 401 (reason `user_inactive`).
- **Rate limiting (auth-service):** register, login, refresh and logout each have a middleware in `auth.router.ts` (built by `createAuthRateLimiters`). The flow is middleware -> `RateLimitService` -> `RateLimiter` interface, all from `packages/rate-limit` (shared with the gateway; `/express` has `createRateLimitMiddleware`, which takes a `readIdentifiers` function); only `server.ts` names `RedisFixedWindowRateLimiter`. A rule's scope is a string: `ip` and `user` are stored as is, every other scope is HMAC-hashed with the pepper (a new scope is hashed unless added to `PLAINTEXT_SCOPES`). auth-service keeps what is its own in `src/rate-limit/`: each endpoint is one policy in `rate-limit-policies.ts` with its numbers in `rate-limit-constants.ts`, and `rate-limit-identifiers.ts` reads the email and refresh token from the body (register 5/IP and 3/email per hour; login 20/IP and 10/email, refresh 60/IP and 20/token, logout 60/IP, all per 15 minutes). Rules run IP first and stop at the first denial. Emails and refresh tokens are keyed as HMAC with `RATE_LIMIT_KEY_PEPPER`, never in plaintext. Past a limit: `TooManyRequestsError` (429, `Retry-After`, `RateLimit-*`). If Redis is down, register and login answer `ServiceUnavailableError` (503) and refresh and logout let the request through with a warning. `TRUST_PROXY_HOPS` (default 0) decides whether `X-Forwarded-For` is trusted; set it to 1 behind the gateway. Tests: `InMemoryRateLimiter` (from `@ticketnest/rate-limit/testing`) for unit tests, a Redis Testcontainer (`redisUrl`) for the integration project; the Redis limiter's own test lives in `packages/rate-limit/test/integration/`. A new auth endpoint needs a policy and a middleware here before it goes through the gateway. See ADR-0013.
- **JWKS (auth-service):** `GET /.well-known/jwks.json` (unversioned, public, internal-only: not routed through the gateway) publishes the public keys. `createSigningKeySet` (`src/auth/signing-key-set.ts`) is built once at startup in `server.ts` from `JWT_PRIVATE_KEY` plus the optional `JWT_ADDITIONAL_PUBLIC_KEYS` (verify-only, max 3) and is the single source for the token signer, the `/me` verifier and `JwksService`; never load keys anywhere else. Only the signing key signs. The response is prebuilt (strong ETag, `Cache-Control: public, max-age=300`, `application/jwk-set+json`), other methods get `MethodNotAllowedError` (405). A new key must be published at least the 300 s max-age before it signs: follow `docs/runbooks/jwt-key-rotation.md`. The rate limiter, if added, plugs into `jwks.router.ts` (the endpoint is internal-only and is not limited today).
- **Docker image:** build from the repo root, `docker build -f services/auth-service/Dockerfile -t ticketnest/auth-service .`. It bundles the service, runs it on bare Alpine as a non-root user with only the Node binary, and needs `DATABASE_URL`, `REDIS_URL`, `RABBITMQ_URL` (unless `OUTBOX_RELAY_ENABLED=false`; on the compose network the hosts are `postgres`, `redis` and `rabbitmq`) and `RATE_LIMIT_KEY_PEPPER`, plus the `JWT_*` variables. The bundle has no pino transport, so pretty logs work only under `pnpm dev`. Install scripts are allowed only for esbuild, prisma and @prisma/engines (`allowBuilds` in `pnpm-workspace.yaml`).
- **API gateway (`services/api-gateway`, port 4000):** the only service meant to be reachable from outside. It is the skeleton without Postgres, and `/health/ready` checks nothing on purpose: Redis only backs a limiter that fails open, so reporting it would pull every replica out of rotation during a Redis outage. `proxy/proxy.router.ts` fixes the order: IP limit (`gateway-ip`, 300/min) -> body-size guard (`MAX_REQUEST_BODY_BYTES`) -> route resolution -> authentication by mode -> user limit (`gateway-user`, 120/min by `sub`) -> forward. Both limits fail open; numbers are in `rate-limit/gateway-rate-limit-constants.ts` and are starting values.
  - **Routes:** `routes/route-table.ts` maps a path prefix (whole segments, longest first) to `auth` or `catalog`. It is an allowlist: an unlisted path is a 404 and is never forwarded (so `/.well-known/jwks.json` and `/healthz` stay unreachable); a `..` or `%2f` segment is a 400. A new service needs a prefix there, an origin in `config.ts` and a breaker in `server.ts`. Booking and payment have no spec, so no entry.
  - **Access modes:** default `required`. `routes/access-rules.ts` lists the exceptions by method and path: `public` never reads the token, `optional` verifies one only if it is sent (invalid = 401, never a silent downgrade). `test/unit/routes/access-rules.test.ts` compares the list and the route table with `security` and the paths in `docs/api/*.yaml`, so change the spec and the gateway together. Guest and email-proof tokens are not verified yet (ADR-0014), so no booking route is listed. Public auth endpoints that auth-service has not built (email verification, password reset, guest sessions, email OTP) stay out of the list and keep the default `required`, named in `UNBUILT_PUBLIC_AUTH_OPERATIONS`; move one into `ACCESS_RULES` together with its rate-limit policy and middleware.
  - **Forwarding:** `ForwardService` runs over the `UpstreamClient` interface; `UndiciUpstreamClient` is the only class that names undici (no redirects, no decompression, one pool per service, timeouts in `proxy/proxy-constants.ts`). A GET or HEAD is retried once when the service is unreachable, never a write and never a timeout. One `CircuitBreaker` per service (5 failures in a row, 10 s open; a 502/503/504 answer counts, a 500 does not). Every answer from auth-service carries `Cache-Control: no-store` (the gateway sets it, whatever the service sent, because those answers can carry tokens). Failures are problem+json: timeout 504 (`GatewayTimeoutError`), unreachable 502 (`BadGatewayError`), open circuit 503 with `Retry-After`.
  - **Headers:** requests carry only the allowlist in `proxy/request-headers.ts`; `Authorization` crosses unchanged (every service verifies again, no identity headers, ADR-0013). `X-Forwarded-For` is overwritten with the gateway's own resolved `request.ip`, so services keep `TRUST_PROXY_HOPS=1` whatever sits in front of the gateway (its own `TRUST_PROXY_HOPS` is 1 behind an ALB, 0 locally). From responses it drops hop-by-hop headers, `Server`, `X-Powered-By`, `X-Request-Id` and `Access-Control-*` (CORS is decided by the gateway alone).
  - **Config and run:** `AUTH_SERVICE_URL` and `CATALOG_SERVICE_URL` are bare origins; the JWKS is fetched from `AUTH_SERVICE_URL/.well-known/jwks.json`, so `JWT_ISSUER` and `JWT_AUDIENCE` must equal auth-service's. In production both service URLs must be `https://` or startup fails; `ALLOW_INSECURE_UPSTREAMS=true` accepts `http://` and is meant only for a private network such as the compose network. Locally `pnpm --filter @ticketnest/api-gateway dev` with auth-service started with `TRUST_PROXY_HOPS=1`. Docker: `docker build -f services/api-gateway/Dockerfile -t ticketnest/api-gateway .`; compose still holds only the infrastructure.
- **Prisma (auth-service):** pinned to the stable 7.10.x line in the catalog (`latest` on npm is an 8.0 RC). The client is generated into `src/generated/prisma` (git-ignored) by the service's `postinstall`; run `pnpm --filter @ticketnest/auth-service db:generate` after editing `prisma/schema.prisma`. The connection URL comes from `DATABASE_URL` (`services/auth-service/.env`) through `prisma.config.ts`. Only `src/repositories/` imports the generated client; `createPrismaClient(pool)` reuses the `pg` Pool and is wired in `src/compose-auth-router.ts`. The generated client reads `import.meta.url`, so the esbuild `build` script defines it from `__filename` for the CJS bundle (without that the bundle crashes at startup).
- **Migrations:** `db:migrate:dev` (local, needs the `CREATEDB` right the init script grants; on an old volume run `ALTER ROLE auth_service CREATEDB` once, or `pnpm infra:reset`), `db:migrate:deploy`, `db:migrate:status`. Create with `pnpm --filter @ticketnest/auth-service exec prisma migrate dev --create-only --name <change>`, review the SQL, then apply. See `.claude/rules/database.md`.
- **Tests live in `test/`, never in `src/`** (rule: `.claude/rules/testing.md`; `pnpm lint` enforces it). Services use `test/unit`, `test/integration` and `test/support`; packages and apps use one `test/` mirroring `src/`. Tests import production code as `@/...` (`paths` in `tsconfig.json` plus `resolve.alias` in `vitest.config.ts`).
- **Integration tests:** the files under `test/integration/` form a second Vitest project that starts a throwaway `postgres:17.11-alpine` through Testcontainers (Docker must be running) and applies the real migration SQL. `pnpm exec vitest run --project unit` skips them.

## Architecture (big picture)

Six services plus two Next.js apps, each service owning a private Postgres database (no cross-service reads or shared tables). Naming: the identity service is **`auth-service`** everywhere (an earlier `identity` name was renamed).

- `api-gateway`: routing, rate limiting, JWT verification. No business rules or data.
- `auth-service`: users, permission-based RBAC (roles are editable bundles of permissions), tokens, guest sessions, email OTP.
- `catalog-service`: operators (tenants), venues/screens, movies, stations/routes/trains, schedules (shows/trips/runs), prices, cancellation policy and fee config, search.
- `booking-service`: seat inventory, Redis holds, bookings, train segment logic, **saga orchestration**, tickets.
- `payment-service`: Stripe PaymentIntents/webhooks/refunds, refund approval queue.
- `notification-service`: email, SMS, web push, DB-backed reminder scheduler.
- `web` (customers) and `console` (admin/operator) call only the gateway.

Cross-cutting rules that span many files:

- **No double-booking, ever.** Redis `SET NX PX` holds (10 min) are a fast pre-filter only. The arbiter is a Postgres unique constraint on `SeatClaim(schedule, seat, segment)`. Trains claim one row per journey segment, so overlap is detected by the constraint. A sweeper (not Redis keyspace events) expires holds.
- **Booking saga is orchestrated inside booking-service**: hold, create booking (sync call to payment for the PaymentIntent), Stripe webhook, `payment.succeeded`, confirm. A payment landing after hold expiry re-claims the seats if free, otherwise triggers a full refund. Booking status and refund status are separate fields; the refund lives in payment.
- **Events:** RabbitMQ topic exchanges per producing domain (`auth.events`, `catalog.events`, `booking.events`, `payment.events`), one quorum queue per consumer, retry queues then DLQ. Every publisher uses a **transactional outbox** (polling relay, `FOR UPDATE SKIP LOCKED`); every consumer uses an **inbox** table and guarded state transitions. Delivery is at-least-once, so handlers must be idempotent.
- **Idempotency layers:** `Idempotency-Key` on client commands, deterministic Stripe keys (`pi:{bookingId}`, `refund:{refundId}`), webhook dedupe on `event.id`, unique dedupe keys for notifications.
- **Snapshots:** booking stores a schedule snapshot and cancellation-policy snapshot at hold time, so later policy edits never change existing bookings and cancelling needs no call to catalog. Events carry the data consumers need (no callbacks).
- **Auth:** asymmetric JWT, 10-minute access tokens with `role`, `permissions[]`, `tenantId`; the gateway and each service both verify. Guests use an anonymous `sid` token for holds. Guest booking lookup uses an email-proof token from auth-service; the **booking** service (which holds the data) checks that the booking reference matches the email.
- **Tenancy:** operator-owned rows carry `tenant_id`; other tenants' resources answer `404`, not `403`.
- **Money and time:** integer minor units (cents, USD), never floats; UTC timestamps with the IANA timezone stored on venues/stations.

API conventions (`docs/api/common.yaml`): `/v1` versioning, RFC 9457 `application/problem+json` errors, cursor pagination returning `{ data, page: { limit, nextCursor, hasMore } }`, `PATCH` as JSON Merge Patch, optional `ETag`/`If-Match`. The Zod schemas in `packages/contracts` mirror these (`Problem`, `Page`, `Money`, `EventEnvelope`) and are hand-maintained, so change the OpenAPI and Zod together.

## Rules

Short, enforceable rules live in `.claude/rules/`:

- `.claude/rules/data-access.md` (scoped to `services/**`): table ownership, repository-only writes, service-layer transactions, outbox publishing.
- `.claude/rules/code-quality.md` (always loaded): layering and DI, DRY, naming, and the code checklist.
- `.claude/rules/testing.md` (always loaded): where tests live (`test/`), the `@/` alias, and how to write them.
